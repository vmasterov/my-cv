## TVIL.RU — Senior Frontend Engineer (Mar 2026 – Present)

Контекст: ~730 Vue-компонентов, 57 страниц, разветвлённый стор. Инкрементальная миграция Nuxt 2 → 3 в живом продукте: Vuex и Pinia сосуществуют через accessor-адаптер, Options API рядом с Composition API, JS и TS в одной кодовой базе.

### 1. Реферальная программа: 10+ модалок → единая модель по сценариям
- **Задача.** Редизайн цепочки модалок акции «Для друзей» (эпик ~30 задач): вход, регистрация, подтверждение контакта, окна успеха и ошибок, отдельные сценарии для юрлиц и объектов без категорий.
- **Как.** Единый набор паттернов для 10+ взаимосвязанных компонентов. Какое окно и состояние показывать, выбирается по контексту открытия (типу сценария), а не разрозненными условиями. Новый дизайн шёл под фичефлагом: флаг прокидывался через параметры точек входа, после проверки включён глобально и снят, логика переведена на выбор по типу сценария. Добавлены остаток бонусов после списания и события аналитики. Стили: mobile-first SCSS, кастомизация базовых компонентов через CSS-переменные.
- **Почему это сеньорно.** Меньше связности: новый сценарий — это новая запись, а не новые ветки if. Безопасный релиз на высоконагруженном продукте.
- **Уточнить:** как был устроен маппинг «сценарий → окно» (словарь, конфиг, компонент-диспетчер); есть ли метрики регистраций по рефералке; как тестировали.

### 2. Фичи в legacy и мигрированных слоях, перевод на TypeScript
- **Как.** Писал фичи в обоих слоях (Vuex + Pinia, Options + Composition API). Типизировал компоненты на TypeScript с Composition API, удалял неиспользуемый код, расставлял data-testid для автотестов.
- **Сложности.** Обратная совместимость слоёв; типизация поверх нетипизированного Vuex.
- **Уточнить:** как работает accessor-адаптер Vuex ↔ Pinia; по каким критериям компонент переписывается сразу, а какой остаётся на Options API.

### 3. Гонки при определении режима пользователя (гость / владелец)
- **Проблема.** После входа режим вычислялся одновременно с восстановлением состояния (гидратация SSR, localStorage) → гонки, неверный режим, ломались редиректы при переключении кабинетов.
- **Решение.** Две фазы: (1) сброс режима при восстановлении состояния; (2) вычисление после загрузки пользователя.
- **Результат.** Гонки ушли, редиректы при переключении кабинетов работают.
- **Уточнить:** как воспроизводили баг; почему не хватило одного await; как проверяли разницу между SSR и клиентом.

### 4. Playwright E2E на desktop и mobile
- **Что покрывалось** (⚠ уточнить, что делал лично — инфраструктуру строил не ты):
  - эпик автоматизации техподдержки (~40 задач): автоответы новому и вернувшемуся пользователю, счётчик входящих, сообщение от поддержки, смена темы, возобновление обращения;
  - главная страница (12 задач) с привязкой автотестов к work items в TestIT;
  - отзывы гостя (8 задач): сквозной флоу от заявки до бонусов; начисление асинхронное → expect.poll;
  - свайп карусели синтетическими TouchEvent (в WebKit через document.createTouch), сдвиг проверяется через boundingBox;
  - фикстуры управления состоянием бэкенда (модерация отзыва, закрытие диалога, перевод заявки по статусам);
  - параметризованный набор тестов каруселей вместо дублирующихся спек.

### Истории «о сложном баге» (в профиль не вошли)
- **iOS.** Нижняя шторка с полем ввода ломалась при появлении клавиатуры. Прокрутка в шторке не работала: блокировка скролла гасила касания, а эмуляция в Chrome этот баг не показывает — воспроизводится только на реальном устройстве. Гонка в маске телефона.
- **URL карты с undefined.** Симптом: `/city/kazan/undefined?...#map`. Причина: deep-watcher позиции карты вызывал pushState раньше ответа сети, `route` ещё пустой → строка «undefined?...»; путь относительный, поэтому приклеивался к текущему «каталогу». Воспроизведение: подвигать карту, перезагрузить страницу. Фикс: guard `if (!route) return`; лучше — заполнять route из текущего `$route`. ⚠ Закоммичен ли фикс — неизвестно.
- **Sentry.** Undefined в адресе карты, ошибки IntersectionObserver и scrollTop, падения на null; диагностика 403 от геоподсказок; дедупликация ошибок; замена perfect-scrollbar нативной CSS-прокруткой.

### 3. Библиотека стандартов (SOP) на server-driven dynamic forms
- **Что это.** SOP — документ с порядком выполнения работ. Пользовательский путь: «Новый стандарт» → попап с обязательными полями → стандарт создаётся на сервере → переход на редактирование (тексты с периодами действия, параметры, свойства, изображения с редактором).
- **Архитектура.** Данные для формирования стандарта приходят с сервера. Клиент определяет типы полей, выбирает компоненты для отображения, валидирует, собирает ответ и отправляет на сервер. Ты писал требования и user flow.
- **Почему это сеньорно.** Форма не захардкожена: при изменении структуры на сервере клиент подстраивается без переписывания экранов.
- **Уточнить:** формат описания полей; как устроен маппинг «тип → компонент» (реестр компонентов?); чем валидировали; как обрабатывали вложенные и повторяющиеся блоки.

### 4. Чек-листы на базе стандартов
- **Что это.** Чек-лист — упорядоченный список действий, каждое ссылается на стандарт (связанные данные).
- **Флоу.** Создание через попап → вкладка «Список действий» → сайдбар добавления действия (выбор стандарта, график выполнения) → вкладка «График выполнения»: сетка дни × смены; клик по ячейке открывает меню, пункты которого зависят от состояния действия (выполнено / не выполнено, есть / нет отклонения): выполнить, отменить, редактировать, посмотреть, внести отклонение.
- **Уточнить:** как моделировали состояния (state machine или условия); синхронизация через TanStack Query (оптимистичные обновления?).

### 5. −25% времени на фронтенд: шаблон декомпозиции + MCP-сервер
- **Суть.** Шаблон декомпозиции задач и MCP-сервер, который записывает ключевые вехи в файлы; AI-инструменты восстанавливают контекст прошлых сессий.
